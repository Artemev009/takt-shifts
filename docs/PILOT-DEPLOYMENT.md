# «Такт»: переход от демоверсии к пилоту сервисного центра

## Что уже подключено на серверной ветке

- Таблицы D1 для отделов, потребности по часам 00–23, допусков сотрудников, индивидуальных логинов, сессий и биржи смен.
- Учёт потребности по отделам `alpha` (Альфа), `mix` (Микс), `mail` (Почта), `mess` (Мессенджеры), `night` (универсальная ночь).
- Отчёт по отделам: `GET /api/department-coverage?date=YYYY-MM-DD`. Незаполненный норматив передаётся как `null`, а не как 0.
- Утверждённые смены всех сотрудников видны в общем расписании. Чужие ожидающие и отклонённые заявки скрыты от остальных сотрудников.
- Биржа открытых смен: владелец выставляет подтверждённую будущую смену, подходящий сотрудник откликается, руководитель согласовывает перевод. В покрытии считается только утверждённая смена.
- У каждого персонального аккаунта сервер хранит пароль в виде PBKDF2-хеша (180 000 итераций, индивидуальная соль). Сеансы — случайные токены, в базе хранится их SHA-256, браузер получает cookie `HttpOnly; Secure; SameSite=Strict` на 24 часа. Выданный руководителем временный пароль обязательно заменяется сотрудником при первом входе.
- После пяти неуспешных попыток вход блокируется на 15 минут. Руководитель может отключить учётную запись.
- Приложение публикует PWA-manifest, иконки и service worker. После «Добавить на экран Домой» оно запускается в режиме `standalone` без адресной строки; данные при этом по-прежнему загружаются только с сервера и не кешируются офлайн.

## Безопасное внедрение

1. Выполнить миграции `drizzle/0007_pilot_departments_auth.sql` и `0008_shift_market.sql` на **копии** D1. Проверить восстановление и затем выполнить их на пилотной D1.
2. Для доверенных заголовков авторизации ChatGPT Sites **только за верифицированным шлюзом** задать `TRUST_OAI_HEADERS=true`; без такой настройки сервер по умолчанию не доверяет `oai-authenticated-*`. На обычном публичном Cloudflare Worker нельзя разрешать эти заголовки: злоумышленник может их подделать. Настройку флага, шлюза и режима доступа нужно проверить вручную.
3. `MANAGER_EMAIL` должен соответствовать адресу первого руководителя при входе через проверенный Sites SSO. Этот руководитель открывает «Команда и доступ» и задаёт свой логин/пароль с помощью `/api/admin/password`.
4. После этого руководитель создаёт индивидуальные аккаунты сотрудников, указывая отдел, универсальный допуск, логин и временный пароль. При первом входе сотрудник обязан заменить временный пароль. Передавать его нужно через согласованный защищённый канал; реальные пароли **не** хранить в репозитории.
5. В отдельном браузере проверить вход по персональному логину без ChatGPT, просмотр общего расписания, создание и согласование заявки, отключение аккаунта и выход. Если публикация Sites требует авторизации через ChatGPT **до** входа в Worker, публичный вход по логину/паролю будет заблокирован на шлюзе. Тогда нужен отдельный HTTPS-домен/маршрут Worker, либо изменённая политика доступа Sites. Нельзя считать вход работающим до такого теста.
6. Сверить полный штат (~50 сотрудников) и отделы со справочником компании; исходный скриншот за 23.10.2026 содержал 26 записей смен, но не полный кадровый список. Не назначать допуски по одним только именам.
7. Согласовать юридические основания и уведомление сотрудников об обработке данных, режимы хранения, резервное копирование D1, ответственного за восстановление и расследование инцидентов.

## Ограничения, не скрываемые от заказчика

- GitHub Pages (`docs/index.html`) — только интерактивная **локальная демоверсия**. Её данные не синхронизируются между сотрудниками, тестовые пароли не являются рабочими.
- Server Worker и GitHub Pages — две разные конфигурации. Публикация git-коммита сама по себе не доказывает, что Server Worker развернулся, получил миграции и был доступен по новому адресу.
- Виртуальная биржа смен работает как заявка на передачу, не как автоматическое назначение без согласования. E-mail/push и внешние оповещения отсутствуют; уведомления внутри приложения уже есть.
- Сложные требования трудового законодательства, перерывы, максимальные смены за неделю и несовместимости квалификаций требуют согласования с работодателем. Сейчас есть проверки длительности, пересечений на дату и допуска.
- Прогноз загрузки и интеграция 1С пока **не** реализованы: нужны доступ к данным обращений, согласованные метрики SLA и безопасный API.
- Для ночи план задаётся отдельно по часам 22:00–08:00. Смена с `start=22,end=30` означает 22:00–06:00 следующего календарного дня. Плановые и фактические часы нельзя смешивать.

## Автоматические проверки

```sh
bash scripts/build.sh
node tests/workflow.mjs
```

Workflow тестирует менеджера и сотрудника, доступность, отметки времени, заявки, персональную авторизацию, блокировку и сброс доступа, потребность по отделам, обмен сменами и ночной переход через полночь. Это не заменяет нагрузочных, UX- и интеграционных проверок на устройствах сотрудников.

## План перехода к пилоту

1. Одна пилотная точка и 5–10 добровольных участников.
2. Две недели параллельного контроля с текущим процессом, без использования приложения как единственного источника учёта.
3. Сравнить число незакрытых часов, время закрытия смен, ошибки согласования и количество ручных сообщений.
4. Только после успешного пилота масштабировать на остальные отделы и сотрудников.

## Проверка готовности серверной версии (добавлено 27.10.2026)

После применения миграций и настройки персонального пароля руководителя запрос
`GET /healthz` возвращает HTTP **200** и `{"ready":true}`.
Если D1 не подключена, отсутствуют нужные таблицы или нет активного руководителя
с паролем, ответ **503** и `{"ready":false}`.

Проверяйте endpoint **на фактическом адресе серверного приложения**, а не на GitHub Pages.
Это проверка серверной конфигурации, **не** подтверждение успешного входа сотрудников
через внешний шлюз Sites или полноценного сценария на двух устройствах.
В CI дополнительно проверяется самостоятельный вход руководителя по паролю без SSO
и доступ к панели управления. Никаких реальных паролей в репозитории нет.
